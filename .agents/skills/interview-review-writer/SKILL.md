# 面经复盘写作

把一次真实面试整理成可追溯、可复习的复盘，而不是只有标准答案的题库。按用户使用的语言写；没有明确要求时，中文面经使用 [排版与内容骨架](references/review-format.md)。骨架有详细版和精简版，按材料丰富程度取舍，不机械填空。

## 先建立事实边界

- 确认公司、岗位、轮次、日期和材料来源；未确认的字段标为“待核对”，不要从相邻聊天或文件名推断成事实。
- 音视频先取得完整转写；文字回忆只按回忆整理，不声称听过录音。阅读用户提供的简历、项目说明或旧复盘，只用来核对项目事实，不把旧轮次问题移入本轮。
- 先列出问题清单，再写正文：按实际顺序覆盖技术题、项目追问、行为题、反问、面试官介绍的业务与明确反馈。录音不清、回答缺失或无法判断是否为独立问题的片段，保留并标注，不悄悄删去。
- 区分四类信息：录音/原笔记明确记录；根据上下文还原；外部资料补充；个人分析推断。引述面试官反馈时只写确实说过或可从录音观察到的反应；推测不要写成对方评价。

## 写出有用的逐题复盘

每个重要问题至少让读者找得到：面试官问了什么、本人当时怎样回答、哪里对或不对、以后该怎样回答。若面试官追问或评价已记录，也单独写出。未记录的原回答或反馈直接注明“未记录”，不能补造。简单题可以合并短段，复杂题按以下思路展开：

1. 先给问题与原回答的忠实摘要，注明原话还是归纳。
2. 评价准确部分、遗漏和错误；把“表达没讲清”和“技术事实错误”分开。
3. 讲透机制、因果、适用条件和工程上的实际差异，而不只罗列接口名或术语。涉及数字时写计算口径、单位、前提和证据；项目职责要区分自研、适配、调用现有框架。
4. 给一段自然、可在面试中复述的参考回答。它是事后改进，不是当场回答；不要夹入未经证实的个人经历或指标。
5. 对仍需查证的项目参数、术语或回答边界列出核对项。必要时附一两个高价值追问，不无限扩展成百科。

外部查证用于校正技术解释，标明来源或依据；公开面经只能作为补充，不冒充本人被问过的问题。专业结论无法核实时保留不确定性。

## 文档收束与交付

- 开头给基本信息、来源说明和一段有证据的整体判断；记录真实面试流程。主体按真实提问顺序展开，末尾整理反问与答复、最重要的薄弱项和下一轮优先准备。没有材料支持的章节省略或标注缺失。
- 信息量大时先给可速读结论，再做较深的逐题解释；文字回忆较少时保持精简，但仍保留题目、原回答已知部分、讲解和参考回答。
- 输出前逐项核对问题清单，确认没有漏题、混入别的面试、把事后补充写成当场发言，或把面试官沉默写成正负反馈。优先修正事实和遗漏，再润色措辞。
- 默认交付可审阅草稿。只有用户要求发布/归档且目标与权限明确时才写入外部文档；若发布到富文本平台，使用真实标题、列表、引用和代码块，不把 Markdown 标记或管道表格当正文，并回读验证。飞书目录、索引与权限操作交给相应集成流程处理。
