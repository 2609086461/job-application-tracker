# Review Writing Rules

## Content

The goal is to reconstruct the interview, explain weak answers and produce wording the candidate can reuse. A technical question normally includes:

1. the question as recorded or carefully reconstructed;
2. the candidate's actual answer;
3. accurate parts and corrections;
4. a plain-language explanation of mechanism, causality and boundaries;
5. a concise answer that can be spoken in a later interview.

Use the real interview order. Include basic information, process, project follow-ups, reverse questions, overall evaluation and next-round priorities when the source supports them. Do not turn the document into a generic question bank.

## Fact Boundaries

- Read the resume, project notes and earlier reviews before rewriting project answers.
- Mark uncertain numbers, chip models, performance claims and responsibility boundaries for confirmation.
- Distinguish vendor BSP adaptation from writing a complete driver from scratch.
- Keep public interview questions separate from the user's actual interview record.

## Feishu Publishing

- Convert Markdown headings into real Feishu heading blocks; do not leave `###` visible in body text.
- When updating, delete the old top-level body before uploading the replacement. Appending a second full copy is not an update.
- Re-read `raw_content`, root child count and key headings after publishing.

## Index And Deduplication

- Query by company, position, round and date before creating a record.
- Update the same event rather than creating duplicates after retries or wording changes.
- After a review is complete, mark its preparation entry complete or archived.
- Deleting or merging duplicate records requires explicit authorization.
